# 设计原则

这份文档记录**为什么这么做**，以及**哪些做法被否决了、为什么**。
被否决的部分同等重要——它们是被实测数据淘汰的，不是凭直觉排除的。

---

## 原则 1 · 释义挂在「出现」上，不挂在「词」上

### 问题

词典给一个词条的是**义项集合**。ECDICT 的 `play` 长这样：

```
n. 游戏, 游玩, 玩笑, 运动, 比赛, 赌博, 跳动, 表演, 剧本
v. 玩, 游戏, 假装, 开玩笑, 比赛, 扮演, 演奏, 演戏, 传摇曳, (使)跳动
```

而 `The play was very interesting.` 里它只有一个意思：**戏剧**。

如果把释义存在「词」这一层，那么：

- 要么把九个义项全列出来（学习者自己猜）
- 要么**硬选一个**，然后在别的课文里选错

**实测**：改造前 3,573 个有释义的词条里，**49.8% 把多个义项打包在一个字符串里**，
覆盖 49.3% 的命中。而且不只是"多"，有时候是**错的**：

| 原句 | 词 | 显示的释义 | 实际 |
|---|---|---|---|
| `on the left` | left | leave 的过去式；**离开；留下** | 在左边 |
| `of course` | course | **路线；课程** | 当然 |
| `Excuse me!` | excuse | **原谅；借口** | 劳驾 |

`left` 显示「离开」、`course` 显示「路线」——**这是在教错**。

### 解法

数据结构改成 `hit = [kpId, start, end, glossIndex, methodIndex]`，
课文级带一个去重的 `glosses[]` 表。

关键点：**数据模型必须先预留这个槽位**。`hits` 早就是 `[kpId, start, end]` 三元组，
说明「出现」这个层级本来就存在，只是释义挂高了一层。

> **推广**：任何"一个对象有多个可能取值、取值由上下文决定"的场景，
> 都要先问清楚「上下文挂在哪个层级」，再去设计存储。

## 原则 2 · 优先级必须显式，且每一级都要能回答"为什么排在前面"

最终的优先级链：

```
原文旁注  >  语块  >  LLM 语境判定  >  编辑词表单义  >  词典首义
```

每一级的依据：

| 层级 | 为什么在这里 |
|---|---|
| 原文旁注 | 唯一的「出现级人工证据」，直接描述这一次出现 |
| 语块 | 词在语块里时，**词义由语块承担**——`on the left` 里的 `left` 不该走 `left` 的词义 |
| LLM 语境判定 | 看到完整句子后做的判断，比任何词级信息都更贴近语境 |
| 编辑词表·单义 | 人工整理且只有一个意思 → 可靠；多义的交给词典 |
| 词典首义 | 通用兜底，`frq` 排序保证取到最常用的那个 |

**这条链的价值在于它是可解释的。** 当用户问"为什么 `left` 是「在左边」"，
答案是"它落到了语块层，语块 `on the left` 的意思是「在左边」"——
而不是"模型觉得是这样"。

## 原则 3 · 先量化，再花模型钱

机械层（词性过滤 + 语块覆盖 + 原形回退 + 词典首义）跑完是 **99.6% 覆盖**。
真正需要 LLM 的只是**词典打包义项**那一类——而那一类里：

```
A 档（≥20 次）   218 个词条  覆盖 8,736 次命中（27.5%）
B 档（5–19 次） 1,062 个词条
C 档（2–4 次）  1,835 个词条
D 档（仅 1 次） 2,790 个词条
```

**D 档有 2,790 个词条各只出现一次。** 为它们调模型是纯浪费——词典兜底完全够。

> **纪律**：在不知道真实规模之前，不要启动批量任务。
> 「先跑一遍看数字」这一步几乎总会改变计划。

## 原则 4 · 语块只能正向枚举 + 反向验证，不能反向挖掘

### 被否决的四种反向挖掘方法

| 方法 | 结果 | 为什么失败 |
|---|---|---|
| 频率 n-gram | top 全是 `the most` `to get` `went to` `of people` | 频率法**分不清"语法组合"和"词汇语块"**——`the most` 出现 44 次，`point out` 只有 7 次，按频率排序前者永远赢 |
| 动词+小品词 | 被 `going to`（不定式的 to）污染 | 不定式 `to` 和副词性小品词同形 |
| PMI 点互信息 | 挖出 `mrs williams` `rio de janeiro` `fur coat` | PMI 偏爱**专名**与**透明复合名词**，这两类都不是语块 |
| 虚化动词+名词 | 挖出 `have the most` `have the country` | 分不清固定搭配（`take a seat`）和普通动宾（`have the book`） |

三种方法挖出的候选**没有一个是可直接使用的**。这不是调参能解决的——
**"是不是一个语义单元"需要语义判断，频率统计给不出这个判断。**

### 采用的方法

> **候选来自类别枚举（人工按类别写参考词表），语料只做验证。**

新概念上的结果：候选 1,435，存活 **806**，淘汰 629。

那 630 条是**实测**淘汰的，不是保守放弃：

```
take care of(0)   never mind(0)   in a hurry(0)   in person(0)
good luck(0)      feel like(0)    end up(0)       take over(0)
```

**这些搭配在通用英语里很常见，但在新概念四册 65,944 词里一次都没出现。**
硬凑数量只会让"我们覆盖了 N 个语块"这个说法变得不诚实。

### 零死条目是硬断言

曾经定义了 322 条却有 **47 条**在语料里从未匹配上，其中 40 条是凭想象写的。
现在 `data:check` 直接判失败：

```
deadChunks: 0
chunkCoverage: 10.3%
```

## 原则 5 · 验证器必须使用「发货的那张表」

### 这是本次最贵的教训

`verify-chunks.mjs` 一开始**自己现算一张变形表**，而 `knowledge.mjs` 用另一张。
结果：验证器认为 `depend on` 存活，线上却匹配不到 `depends on`。

**假绿**——测试通过，功能不工作。

### 修法

```js
// 刻意用「发货的那张表」而不是现算一张：验证的必须是真正上线的东西，
// 否则验证通过而线上匹配不到，就是假绿。
import { VERB_FORMS } from './verb-forms.mjs';
```

这个坑最终是被 `data:check` 的死条目断言抓出来的——**验证器与被验证对象不一致**
是一类隐蔽 bug，只有"端到端断言最终产物"才能发现。

> **推广**：验证代码与被验证代码不能各自持有一份真相。
> 让验证器 import 生产代码的产物，而不是复制它的逻辑。

## 原则 6 · 给"约 N 个"这类指标下结论前，先证明测量工具没坏

### 我在这件事上错了两次

**第一次**：我算出语块上限是 591，理由是 493 个候选零命中。

**第二次复查**发现验证器有三个 bug：

| Bug | 影响 |
|---|---|
| 占位符当字面量 | `at one's best` 里的 `one's` 在语料里从不字面出现 → 成批假死 |
| `be` 后没有副词槽 | 语料是 "am **very** proud of" → **整类 `be+形容词+介词` 全废** |
| ECDICT 的 `be` 变形表不完整 | 只有 `be/being/was/been/is/bes`，**缺 `am`/`are`/`were`** |

修完三个 bug + 补四批候选，从 591 一路推到 **806**。

### 该做的动作

在给出"上限"类结论之前，**抽查已知应该存在的项**：

```
in particular   → 0 次    ✓ 确实没有
in person       → 0 次    ✓ 确实没有
in fact         → 14 次   ✓ 在册
give up         → 4 次    ✓ 在册
```

只有抽查通过，那个"上限"才可信。

> **推广**：「达不到 N」是个强结论。它是关于**工具**的断言，
> 而不只是关于**对象**的断言。先验证工具。

## 原则 7 · 源文的残缺不补写，标注出来

新概念源文件有 168 处格式问题：标题与首句粘连、拼写错误（`mater` 应为 `matter`）、
截断的首句、两个 Lesson 27。98 个词形是源文粘连产物（`andforgive`、`beautif`、`determinded`）。

**处理方式**：原样保留 + 在 `quality[]` 里标注 + UI 折叠显示。

**不补写的理由**：

- 补写会掩盖问题，让"这份文本可信"变成谎言
- 学习者会照抄错误
- 源文位置的可追溯性（`sourceBlock + sourceStart`）一旦被改写就失效了

对应地，词典查不到那 98 个词形时**不伪造释义**——`contextWords` 统计里如实计入。

## 原则 8 · 小步可验证的交付节奏

每个阶段都有**独立的数字产出**，不需要等全流程跑完才知道对不对：

| 阶段 | 独立指标 |
|---|---|
| 词典层 | 词条命中率 98.7% |
| 词形层 | 覆盖 174 个动词 |
| 标注层 | 46,393 个命中，位置全部合法 |
| 语块验证 | 存活 805 / 死条目 0 |
| 机械消歧 | 覆盖率 99.6% + 方法分布 |
| LLM 增强 | 接受 8,553+815 / 拒绝 1 |
| 产出 | 221,970 项断言 |

这个节奏让"哪里坏了"在每一阶段结束时就能定位，而不是最后一起爆。

## 原则 9 · LLM 输出必须在候选集内选择，或受机械约束

### 有候选集的任务（词义）

```
输入：句子 + 目标词 + 候选义项数组
输出：只返回下标 index
```

得到的是**可枚举、可校验**的结果。如果让模型自由生成中文，同一个词同一个意思
会在不同课文里写成"私人的"和"私密性的"——**全库不一致，学习者建立不起稳定印象**。

### 没有候选集的任务（句子结构分析）

改用三条**机械可验证**约束：

| 约束 | 为什么有效 |
|---|---|
| `skeleton` / `modifiers[].text` 必须是原句**精确子串** | 模型编不出来（和 hit 偏移同一个技巧） |
| `modifiers[].role` 必须在**封闭词表**内 | UI 才不会长出三十种说法 |
| `grammarRefs` 必须是该句**已有语法点的子集** | 不许自己发明语法点 |

**违反约束整条丢弃。** 新概念上 815/816 通过，唯一被丢的是超长。

### 这一切的前提：构建期而非运行时

结果落成静态 JSON，运行时零延迟、可离线、**可 diff、可审查、可提交**。
这同时满足了项目"运行时不产生模型请求费用"的约束。

## 原则 10 · 诚实的展示基础设施要提前建

应用早就有：

- `provenance` 字段（`source-inline` / `editorial` / `context` / `editorial-morphology`…）
- 词条详情里的「注解来源」折叠区

所以新增的 `llm` / `chunk` / `editorial-single` 等来源**直接挂进去就行**，
不需要改 UI 结构。

结果是：学习者随时能看到「这个释义是**课本原注**、**语块**、**语境判定**、
**整理词表**还是**词典**」——**来源可见，才有信任**。

## 附：本次会话中被否决的方案汇总

| 方案 | 否决理由 | 替代 |
|---|---|---|
| 释义存在词级 | 49.8% 打包多义，且会教错 | 存在出现级（原则 1） |
| 从语料反向挖掘语块 | 四种方法全部失败，噪音不可控 | 类别枚举 + 语料验证（原则 4） |
| 让 LLM 自由生成中文释义 | 全库不一致，无法校验 | 候选集内选下标（原则 9） |
| 用 `grammar`/`pattern` 区间做语块覆盖 | 语法命中常横跨整句，不是语义单元 | 只用 `chunk` 区间 |
| 按词性重排 ECDICT 义项 | 破坏了词典自身的"常用度排序" | 保留原序，`first-sense` 即核心义 |
| 用 `posRatio` 决定词性 | ECDICT 的 `pos` 常被 `other` 占据多数（`good` 是 `other:94/n:4`） | 上下文词性优先，`first-sense` 兜底 |
| 为 D 档（仅出现 1 次）的 2,790 个词调 LLM | 纯浪费 | 词典兜底，模型只处理 A/B 档 |
| 语块硬凑到 800 条 | 会重新制造死条目 | 只收录语料里真实出现的（原则 4） |
| 补写源文残缺（`mater` → `matter`） | 掩盖问题、破坏可追溯性 | 原样保留 + 标注（原则 7） |

## 原则 11 · 外部材料是「证据」，不是「内容」

做教学点抽取时，会自然想直接采纳第三方资料（教材教辅、机构大纲、他人讲义）。
**这条路有风险，必须区分「用什么」和「抄什么」。**

### 四种风险

| 风险 | 具体表现 |
|---|---|
| **版权** | 他人讲义是受版权保护的演绎作品。把它的讲解文字、例句、练习题搬进自己的数据集，等于再分发 |
| **正确性** | 第三方材料有错。本次调研就撞到两次：一份标着「第四册语法总结」的内容其实是**第一册**的；一份标着「第三册」的描述其实是**第二册**的 |
| **版本错配** | 讲义用的教材版本可能与手上语料不同。本次已实测：讲义 L04 是 "in Russia"，我方语料是 "In the Soviet Union" |
| **一致性** | 不同来源的术语、粒度、组织方式都不一样，混着搬会产出一个自相矛盾的知识库 |

### 用法分界

| 可以做 | 不可以做 |
|---|---|
| 用它对**验证**某个教学点确实存在于某一课 | 把它的讲解文字搬进数据集 |
| 用它**发现**自己漏掉的类别（如"写作""近义词"） | 把它的例句当作我方例句 |
| 用它**交叉验证**另一套材料的清单 | 把它的练习题搬进题库 |
| 用它确认**结构**（如"螺旋递进""复习课"） | 把它标注的课际依赖当现成数据用 |

一句话：**外部材料回答"要做什么"，不回答"写成什么"。**

### 正确的产品

教学点必须**从自己拥有的课文语料推导**，外部材料只参与验证：

```
第三方材料  →  候选清单（哪些点在哪些课）
                      ↓
              语料验证（这个点在课文里有没有真凭实据）
                      ↓
              交叉验证（至少两套独立来源一致才采信位置）
                      ↓
              表述自撰（或 LLM 从课文生成 + 机械校验）
                      ↓
              我方 teachingPoint（带 provenance 标注来源）
```

### 配套纪律

- **研究区不进版本库**：抓来的材料放 `.nce4/`、`.llm/` 这类 gitignore 目录，
  只作比对用途。**永远不要转存到 `corpora/` 或 `public/data/`**
- **"提取成结构化 JSON"这个动作本身有风险**：一旦落盘，它很容易被当成本方数据直接使用。
  提取物只放研究区，且文件名要能看出是外部材料
- **例句一律从自己的课文取**。我方语料有 46,000+ 个带精确位置的命中，
  不缺例句，没有理由引用外部材料
- **`provenance` 字段要如实标注**：外部材料只用于验证时，产出的教学点标 `derived` 而不是 `textbook`

### 反例：本次会话中差点犯的错

我曾提议"把 48 份讲义提取成结构化 JSON 供后续使用"。**这个提议本身就有问题**——
它把一个只该用于验证的外部材料，变成了一个看起来可以直接入库的数据文件。
正确做法是：提取物留在 `.nce4/`，只用来核对"某一课是否真的教某个点"，
我方教学点另起一份、从课文推导。

## 原则 12 · 代理指标失效时要去掉它，不要调参

「句子分档」原本把句子标成 **范句 / 长难句 / 例句**，用来告诉读者"哪句值得停下来"。
实现却是两个代理：

```js
tier = wc>=32 || (wc>=23 && clauses>=2) ? 'complex'   // 用"长"代理"难"
     : hasPattern && 4<=wc<=25        ? 'model'      // 用"恰好命中句型正则"代理"值得记"
     : 'example'
```

扩充句型规则（32 → 96）后，这个**没有改动**的规则把范句从 415 推到 918，
占全部句子的 20%。信号被稀释到没有信息量。

### 处理这类问题的顺序

1. **先问代理是否还成立**。这里两条代理都不成立：
   "长"不等于"难"；"正则命中"不等于"这一课教这个"。
2. **再问这个判断能不能真的得到**。教材的教学意图是**人写的**，
   语料统计推不出来（原则 11 的教训）。所以这不是"参数没调好"，是**这个量根本测不出来**。
3. **能去掉就去掉**。分档被去掉后：
   - 视觉信号改由已有的命中高亮承担（句型/语块命中本来就会高亮）
   - 分析范围变成显式的成本选择，不再包装成教学判断
   - UI 少一层会失真的标签

**调参是在保留一个错误的量；去掉是承认它测不出来。**

## 原则 13 · 批次产物必须按内容命名

LLM 批次用过序号命名（`analysis-000`、`analysis-001`…）。
第二次跑时新批次从 000 重新编号，**覆盖了上一轮的同名结果**——
分句分析从 815 条悄悄掉到 781 条，**没有任何测试报警**。

改成按内容哈希命名后，重跑只会新增，不会覆盖。

配套两条：
- **产物目录只增不删**：`llm-prepare` 清 `in/` 不清 `out/`
- **对可静默流失的产物设下限守卫**：测试里断言"分析数不低于 X"，
  而不是断言一个和分档挂钩的比例（比例会随其他改动漂移）

**凡是"按顺序编号 + 会重跑"的产物，都埋着这个坑。**

## 原则 14 · 测量也必须用发货的实现

原则 5 说的是「验证器要用发货的那张表」。这次犯的是同一个错的**另一半**：
**测量时也要用发货的实现，不能自己重写一个近似版。**

做 B4（搭配补齐）时，我判断"语块层系统性漏配动词变形"，依据是：

```
be able to   字面匹配 17 次   含变形 47 次    → 结论：漏 30 次
look at      字面匹配 10 次   含变形 29 次    → 结论：漏 19 次
```

**那个"含变形"的正则是我自己手写的**，不是脚本里真正在跑的那条。
真实实现里有一个后处理循环，用 `VERB_FORMS[首词]` 展开：

```js
const alt = VERB_FORMS[first] || first;
chunk.regex = new RegExp('(?<![A-Za-z])(?:' + alt + ')' + gap + tail + '(?![A-Za-z])', 'gi');
```

拿发货的实现重算：`be able to` 旧 48 / 新 48，**完全一致**。
"系统性缺陷"根本不存在，我修的是一个本来没坏的东西。

### 教训的具体形状

自己写一个"大概等价"的实现来测量，会**同时**产生两个方向的错误：

- 把发货实现**已经做到**的事当成缺失（这次）
- 把发货实现**做不到**的事当成已完成

而且这种错误伪装得很好——数字看起来很具体，还带小数。

### 正确的做法

测量任何东西之前，先问：**"我算的这个量，和脚本里那个量，是同一个东西吗？"**
如果答案是靠一个自己重写的近似版，那测量结果无效。

### 这次附带修掉的真实问题

调查虽然基于错误前提，但翻代码时发现了一个**真实的潜在 bug**：
`chunkRegex()` 构造的正则，紧接着被一个后处理循环**整个覆盖**。
两处构造，一处静默失效——任何人改 `chunkRegex()` 都不会有效果（正如这次发生在我身上）。
已合并为单处构造。

**错误的前提也能撞出真问题，但不能因此把错误的前提说成对的。**
